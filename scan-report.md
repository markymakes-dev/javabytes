## Coexistence option (consider first)

- Run server-side JavaScript on GraalJS (GraalVM) behind Spring Boot and port routes incrementally; this avoids transpilation entirely.
- Keep a REST boundary and rebuild the browser UI in Vaadin, Thymeleaf/HTMX or JavaFX; browser/DOM code has no mechanical Java equivalent.
- Rhino targets older JavaScript editions and is not a fit for modern JS/TS; do not plan a migration around it.
- Java-to-JavaScript tools such as JSweet and GWT solve the opposite problem and cannot convert JavaScript back to Java.

## Phases

- 1. Freeze the JavaScript app and capture its observable behaviour as tests (routes, status codes, validation rules, key user flows).
- 2. Model the domain and database in Java first (entities, constraints, migration scripts). Do not port UI before the data model is stable.
- 4. Run both implementations against the same acceptance tests, then cut over route by route and delete the old code only after parity is proven.

## Risks

- Browser APIs have no mechanical Java equivalent: fetch.
- npm dependency behaviour (transitive versions, lifecycle scripts, native addons) is not reproduced by Java libraries with the same name.
